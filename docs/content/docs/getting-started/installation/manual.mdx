## Download the source code

You can download the source code for Lumexia from the [GitHub repository](https://github.com/isaacvarg/lumexia). 

You can either clone the repository using Git or download it as a ZIP file and extract it
```bash
# clone repo
git clone https://github.com/isaacvarg/lumexia.git
````

## Install Dependencies

The [prerequisites guide](/docs/getting-started/installation/prerequisites) lists and provides instructions on installing required environment dependencies, such as database and object store.

```bash
# change directories into lumexia
cd lumexia

# install node dependencies
npm install
```


## Prepare the database

Migrations must be deployed so that the struture of the database matches the schema, then the prisma client must be generated. 

The database must be seeded with data used throughout the application, such as default statuses, configs, etc. Lastly, static records must be generated. These are files that plainly store records that are often used so that database calls are not needed.

```bash
# prepares the database
npx prisma migrate deploy

# generate prisma client
npx prisma generate

# initializes with necessary seeded data
npm run init

# generate static records
npm run generate-static-records
```

## Seed a demo instance (optional)

To stand up a public **demo** instance that looks "lived-in" — populated with suppliers, products, MBPRs, purchase orders, batch production records, inventory and purchasing requests — run the demo seed **after** the database has been prepared above. It layers transactional dummy data on top of the required reference data, so it must run after `npm run init` and `npm run generate-static-records`.

The demo seed is gated behind the `DEMO_SEED` environment variable so it can never run against a real instance by accident. Set it only on the demo deployment:

```bash
# in the demo deployment's .env
DEMO_SEED="true"
```

```bash
# seed transactional demo data (runs after init + generate-static-records)
npm run seed:demo

# wipe only the demo/transactional data and re-seed back to a fresh start state
npm run seed:demo:reset
```

All demo records are backdated relative to the time you run the seed, so the instance always looks recently active. `seed:demo:reset` leaves reference data and the system user untouched, making it safe to run on a schedule to refresh the demo after visitors poke around.

> A normal production install should **not** run `seed:demo`. Omitting it is the entire separation between a demo instance and a fresh one.

## Start or build 

```bash
# development server
npm run dev

# build
npm run build
```

## First user login 

The first user login create a user with the `System Admin` role. This allows the user to edit company settings, images and user roles
