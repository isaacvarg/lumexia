---
title: Agents (MCP)
description: Let Claude Code, Hermes, and other AI agents read Lumexia data (items, lots, Canon, purchasing, pricing) and file item documents through the built-in MCP endpoint, authenticated with per-user API keys.
---

Lumexia exposes a [Model Context Protocol](https://modelcontextprotocol.io) (MCP)
endpoint so AI agents can look things up the same way a person would: search
items, check lots and QC results, read Canon values and their history, see
which item documents are missing or out of date, download them, look up
purchase orders and purchasing requests, and examine pricing. With a write
key, an agent can also upload and file item documents and approve or reject
pricing examinations.

The endpoint lives inside the app at `/api/mcp`, so there's nothing extra to
deploy. Agents authenticate with an **API key** that acts as a specific Lumexia
user, with that user's permissions.

<Callout>
  Keys are **read-only** unless a system admin gives them write access. Write
  access covers item documents and reviewing pricing examinations: agents
  still can't change inventory, purchasing, or Canon.
</Callout>

## Which agents can connect

Lumexia runs on the local network over plain HTTP, so the agent has to run
somewhere that can reach it:

- **Claude Code** (CLI, desktop app, IDE extensions) runs on your machine and
  connects directly.
- **Hermes Agent** connects directly when it runs inside the network.
- **claude.ai / Claude Desktop custom connectors** *can't* be used. Those
  connect from Anthropic's cloud, which can't reach a server on the local
  network.

## Create an API key

1. Open **Settings → User** and pick the **Agents** tab.
2. Click **New key**, give it a name that says where it'll be used (e.g.
   `Claude Code – desktop` or `Hermes`), and choose when it expires.
3. Copy the key. **It's only shown once.** Lumexia stores just a hash of it.

Make one key per agent or machine, so you can revoke one without breaking the
others. The **Agents** tab shows when each key was last used.

<Callout type="warn">
  A key acts as you. Anything you can see in Lumexia, an agent holding your key
  can see too, including Canon values gated by team permissions.
</Callout>

System admins can see and revoke any user's keys from **Settings → Users →
(user) → Agents**. Admins can't create keys for other people, only for
[agent users](#agent-users).

### Extra access

Keys only read unless a system admin grants more:

| Access | Scope | Lets the agent |
| --- | --- | --- |
| **Write** | `write` | Upload and file item documents, and approve or reject pricing as the key's owner. |
| **Act for linked users** | `delegate` | Act for whoever messages it from a [linked account](#hermes-and-chat-apps), within what the key's other access allows. For shared agents like Hermes. |
| **Propose Canon changes** | `propose` | Open Canon change requests, add evidence, and withdraw its own requests. Never approve or reject. See [Canon proposals](#canon-proposals). |
| **Edit aliases** | `alias:write` | Add, rename and remove item aliases. See [Item aliases](#item-aliases). |

- When an admin creates their own key, they tick what it may do.
- On **Settings → Users → (user) → Agents**, an admin can use **Change access**
  on any of that user's keys. That's how the person who files documents gets a
  write key without being an admin.

The **Access** column shows what each key can do.

## Agent users

A key on your own account acts as you, so everything the agent does shows up
under your name. For a shared or long-running agent (Hermes, a Canon Agent, an
automation), create an **agent user** instead: a Lumexia user that never signs
in and acts only through its API keys.

1. As a system admin, open **Settings → Users** and click **New agent**.
2. Give it a name (shown on everything it does, e.g. `Hermes`) and optionally a
   description (e.g. `Hermes on WhatsApp`).
3. On its page, give it the **roles** it needs under **Profile**. It starts with
   none.
4. Under **Agents**, click **New key** and tick the [extra access](#extra-access)
   it needs. Admins create an agent's keys because it can't sign in to make its
   own.

Agent users get a bot avatar and an **Agent** chip next to their name, and the
**Kind** filter on Settings → Users lists them. Their type can't be changed
later. To retire one, **Disable** it under **Status**: its keys stop working at
once and its history stays. Agents can't sign in with Discord, even if an
account gets linked to them.

To move an agent off your own key, create its agent user and key, put the new
key in the agent's config, then revoke your old key.

The **Lumexia** user is the *system* user: scheduled jobs such as reordering
rules act as it. Its page is read-only, and it can't hold keys.

## Connect Claude Code

After you create a key, the **Agents** tab shows a ready-to-copy command. It
looks like this:

```bash
claude mcp add --transport http lumexia http://<lumexia-host>:3000/api/mcp --header "Authorization: Bearer lmx_..."
```

Add `--scope user` to make it available in every project rather than just the
current directory. Check that it connected with `claude mcp list`, or `/mcp`
inside a session.

## Connect Hermes

Add a server to `~/.hermes/config.yaml`:

```yaml
mcp_servers:
  lumexia:
    url: "http://<lumexia-host>:3000/api/mcp"
    headers:
      Authorization: "Bearer ${LUMEXIA_API_KEY}"
```

and put the key in Hermes's environment as `LUMEXIA_API_KEY`, so the key
itself stays out of the config file.

For a key that [acts for linked users](#hermes-and-chat-apps), also tell
Lumexia which Hermes profile is connecting, so desktop and CLI sessions can be
linked to a person. Add a header with the install id (from
`~/.hermes/install_id`) and the profile name, in each profile's config:

```yaml
    headers:
      Authorization: "Bearer ${LUMEXIA_API_KEY}"
      X-Lumexia-Agent-Identity: "hermes:<install_id>:<profile>"
```

It's set by whoever configures Hermes, so the model can't claim to be another
profile.

## Available tools

| Tool | What it returns |
| --- | --- |
| `whoami` | The user the key acts as, and the key's scopes. Handy to confirm the connection. |
| `search_items` | Items matching a name, reference code, or alias (INCI name, trade name, …), with the alias that matched. Archived items are excluded unless asked for. |
| `get_item` | One item by id or reference code: type, procurement, status, all aliases, and total quantity on hand. |
| `get_item_lots` | An item's lots with supplier lot, expiry, quantity on hand and origin (purchase order and supplier, or batch). Only lots with stock unless asked, newest first. |
| `get_lot` | A lot by our lot number or the supplier's: item, supplier lot and dates, quantity on hand, origin, how it was received (inspection, flags), QC records with every parameter result, and notes. Lot numbers can repeat across items, so this may return several. |
| `get_item_canon` | Every [Canon](/docs/canon) data type for an item, as plain text, with status, flags, version, open change requests, and whether you can edit or review it. Includes supplier statements and finished products filled with the item. |
| `get_canon_history` | Every accepted version of a Canon value with its change request, reason, reviews, and evidence, plus open change requests and events. |
| `get_canon_review_queue` | Change requests waiting on your review, and stale, expired, or conflicting values you edit or review. |
| `get_canon_data_types` | Every active Canon data type and its setup: group, shape and the JSON value format to propose, subject, authored or linked source, what it applies to, dependencies, approval rules, evidence requirement, re-verification period, website key, and who can edit and review it. |
| `search_canon_artifacts` | Canon values across items, for sweeps: filter by data type, group, status, flags (stale, unreviewed change, expired, conflict), open change requests, or item. |
| `get_item_bom` | The bill of materials of an item's active MBPR: each material with id, reference code, concentration, step and phase. |
| `get_material_documents_for_bom` | `get_item_documents` for every material in an item's active BOM, in one call. |
| `list_alias_types` | The alias types and which are unique (one item per name). |
| `list_document_types` | The document types (SDS, COA, IFRA, TDS…) with their ids. |
| `search_suppliers` | Suppliers matching a name or alias, e.g. the company printed on a document. |
| `get_item_documents` | An item's [document requirements](/docs/inventory/item-documents) and their status, per-lot status for lot documents, and every document on file including replaced versions, with the supplier lot and PO each was filed for and whether it's still waiting for its lot. |
| `get_document_issues` | Required documents that need attention across all items (missing, expired, mismatch, expiring, undated, stale), with the supplier to ask when known. Filter by status, issuer, item, document type, or supplier. |
| `find_documents_by_checksum` | Whether files (by MD5, from `md5sum`) were already uploaded, and which item documents they're attached to. |
| `get_document_downloads` | Download links for item documents, valid 15 minutes. The agent saves each with `curl -o`, so the file never passes through the model. |
| `search_purchase_orders` | Purchase orders, newest first, with supplier, status, lines, and total. Filter by supplier, item, status, or creation date. Cancelled orders are left out unless asked for. |
| `get_purchase_order` | One PO by reference code: lines with expected delivery and received lot, payment method, accounting status (paid, packing slip), notes, and the requests it fills. |
| `get_item_purchase_history` | Every PO line for an item with supplier, quantity, unit, and price per unit, plus the last price, which is the one pricing uses. |
| `search_purchasing_requests` | Purchasing requests with status, priority, expected delivery, suppliers, and linked POs. Open requests only by default, like the requests dashboard. |
| `get_purchasing_request` | One request by reference code: linked POs and their lines for the item, linked batches, the inventory snapshot taken when it was made, and notes. |
| `get_item_pricing` | An item's current pricing: pricing data, last purchase price, the resulting item cost, the finished products filled with it (costs, consumer price, markup, profit), and recent examinations. |
| `search_pricing_examinations` | Pricing examinations by item or status, e.g. `pendingReview` for the review queue or `queued` for items waiting to be examined. |
| `get_receiving_issues` | Deliveries received since a given time whose lines need a look: failed dock inspection, more or less than ordered, no supplier lot, a required lot document (COA) missing, or a COA for another supplier lot. Document flags clear once the document is on file. See [Receiving alerts](#receiving-alerts). |
| `get_document_inbox` | Documents waiting in the [document inbox](/docs/inventory/item-documents#document-inbox): who sent them, the email subject and link, the supplier matched from the sender, the agent's suggestion or filing, and where an identical file is already on file. Each has a download link valid 15 minutes. Views: `review` (default), `pending`, `agentFiled`, `filed`, `dismissed`. |
| `get_pricing_examination` | One examination as it was snapshotted: pricing data, finished products, consumer containers, and for produced items the batch costing with every BOM material's price and where it came from. Plus validation and notes. |

Keys with write access also get:

| Tool | What it does |
| --- | --- |
| `create_document_upload` | Returns single-use upload links, valid 15 minutes. The agent uploads each file with `curl -F file=@…`, so file contents never pass through the model. PDFs and images, up to 50 MB. |
| `attach_item_document` | Files an uploaded document under an item with its type, issuer, supplier, lot, supplier lot, PO, dates, revision, and the supplier document it's based on. Given only the supplier lot, it goes on our lot with that supplier lot, or waits until one is received. Like uploading in the Files tab, it replaces older versions of the same document and reports other current versions from a different supplier. |
| `update_item_document` | Changes a filed document's details. Never replaces other documents. |
| `set_document_replaced` | Marks a document replaced, or restores it as current. |
| `file_inbox_document` | Files an inbox document under an item, with the same details as `attach_item_document` and a required `reason`. No upload needed. It shows in the inbox as filed by the agent until someone checks it. |
| `file_inbox_document_to_purchase_order` | Files an inbox document (invoice, packing slip…) on a PO's accounting files, with a reason. |
| `suggest_inbox_document` | Leaves the agent's best guess (item, type, supplier, supplier lot, PO, dates, confidence) and reason on an inbox document it couldn't file. It prefills the filing form for whoever files it. |
| `approve_pricing_examination` | Approves an examination that's pending review, as the key's owner. |
| `reject_pricing_examination` | Rejects one, with an optional reason added as a note. Like the app, it queues a new examination of the item that carries the notes forward. |

Keys that [act for linked users](#hermes-and-chat-apps) get the two pricing
tools too, but record the review as the person who sent the message, plus:

| Tool | What it does |
| --- | --- |
| `identify_sender` | Which Lumexia user a WhatsApp, Discord, Telegram or Slack account, or a Hermes profile, is linked to, or how to link it. |
| `link_identity` | Links the sender's account to their Lumexia user with the code they created in Lumexia. |
| `unlink_identity` | Unlinks the sender's account. |

Keys that may propose Canon changes get the tools in
[Canon proposals](#canon-proposals), and keys that may edit aliases get those
in [Item aliases](#item-aliases).

Tools accept either an item's id or its reference code, so an agent can go
straight from "what's on hand for ING-1006?" to an answer. Purchase orders and
purchasing requests are looked up by their reference code (`PO-123`, `#123`,
and `123` all work).

Purchasing and pricing tools are read-only for every key, including write keys.
Payment methods show their name only, never account details.

## Filing documents from a folder

With a write key, Claude Code can work through a folder of supplier and branded
documents for you. It reads each file, works out which item it belongs to, and
files it with the right type, issuer, supplier, lot, and dates.

1. Open Claude Code in (or with access to) the folder, connected with a write key.
2. Paste a prompt like this:

```text
File the documents in this folder into Lumexia. For each file, work out the
item, document type, whether it's the supplier's document or our own branded
version, the supplier, our lot number for COAs, the issue date, and revision.
Check checksums first and skip anything already uploaded. Show me a table of
what you plan to file before uploading anything, and list any file you can't
match confidently instead of guessing.
```

3. Review the table, fix anything Claude got wrong, and tell it to go ahead.
4. It uploads and files each document, then reports what each one replaced and
   which requirements are now met.

Tips:

- Uploads behave like the Files tab: a new version replaces the older version
  of the same document from the same supplier. If the item already has a
  current version from a different supplier, Claude tells you and asks whether
  to replace it.
- Supplier COAs show the supplier's lot number, and that's enough: Claude passes
  it as the supplier lot and Lumexia puts the COA on our lot received with that
  supplier lot. If that delivery hasn't arrived yet, the COA waits and is
  attached when it's received (and the receiver sees it's already on file).
- Every upload is logged on the item's activity as you, marked "via MCP".

## Documents emailed by suppliers

Purchase orders ask suppliers to send documents to the documents mailbox, often
before the delivery arrives. Every attachment goes into Lumexia's
[document inbox](/docs/inventory/item-documents#document-inbox) first, and the
agent then files what it can:

1. The automation (an n8n workflow watching Gmail) posts each email and its
   attachments to `POST /api/inbox/documents` with a write API key. No model is
   involved, so nothing is lost when the agent can't match a document.
2. The response has an `inboxDocumentId` per file. The agent reads the email and
   the attachments, searches Lumexia, and for each document either:
   - files it with `file_inbox_document` (or `file_inbox_document_to_purchase_order`)
     when exactly one item or PO clearly matches, with its reason, or
   - leaves `suggest_inbox_document` with what it found and why it didn't file.
3. People see unfiled documents and the agent's unchecked filings under
   **Quality → Documents → Inbox**, and file, check, take back, or dismiss them.

Pass the supplier lot printed on each COA (and the PO from the email, if there
is one):

- If the lot was already received, the COA goes straight onto it.
- If not, it's kept as waiting for that supplier lot. At the dock the receiver
  sees "COA on file" as soon as they type the matching supplier lot, and it's
  attached to the new lot when they post the receipt. A COA for this PO with a
  different supplier lot is shown as a possible mismatch.

### The inbox endpoint

`POST /api/inbox/documents`, with `Authorization: Bearer <write key>` and
multipart form data:

| Field | |
| --- | --- |
| `source` | `gmail`, `paperless` or `manual` |
| `sourceId` | Required. The message's id in its source, e.g. the Gmail message id |
| `threadId`, `sourceUrl` | Optional. `sourceUrl` becomes the **Open email** link |
| `senderEmail`, `senderName`, `subject`, `body`, `receivedAt` | Optional. `receivedAt` is an ISO date or epoch milliseconds |
| files | One or more file fields (any name; `files` by convention). PDFs, images, Word, Excel and CSV, up to 50 MB each |

Sending the same message again is safe: files already in it are skipped, so a
failed run can simply be retried. The sender's email domain is matched against
supplier contacts to show which supplier sent it. A file that's identical to
one already filed, or to one dismissed before, arrives already dismissed.

```json
{
  "messageId": "…",
  "supplier": { "id": "…", "name": "Acme Chemicals" },
  "documents": [
    { "inboxDocumentId": "…", "name": "SDS.pdf", "md5": "…", "status": "pending", "dismissReason": null, "alreadyInInbox": false }
  ],
  "skipped": [{ "name": "invite.ics", "reason": "Only PDFs, images and Office/CSV files are accepted." }]
}
```

In n8n, use an HTTP Request node with **Form-Data** body: text fields for the
message and one **n8n Binary File** field per attachment, then hand the returned
ids to the AI Agent node along with the attachments. Marking the Gmail thread
read stays the way to avoid reprocessing.

## Canon proposals

A key with **Propose Canon changes** lets an agent fill in and keep up
[Canon](/docs/canon) values, with people reviewing every change. The agent
proposes; it can't approve or reject.

| Tool | What it does |
| --- | --- |
| `propose_canon_change` | Opens a change request like the Propose form: `edit` (a new value for an authored type), `stale_confirmation` (the value is still right after something upstream changed), or `source_acceptance` (a linked type's current Lumexia value). Takes a reason, evidence (an item document, URL or note, with its date), and an `idempotencyKey`. Returns the change request (`CR-104`), the diff, the approvals needed and who can review. |
| `attach_canon_evidence` | Adds evidence to any change request still under review. Never changes the proposed value. |
| `withdraw_canon_change` | Withdraws a change request the key's user opened. |

How it behaves:

- **People decide.** A change request opened through MCP never counts the
  requester's own approval, even if they could review. A key that acts for
  linked users is refused with `AGENT_MUST_NOT_REVIEW` if its user holds Review
  on the data type.
- **Who asked.** The requester is the key's user (e.g. a **Canon Agent** user).
  When a key acts for linked users, the person who directed the change is
  recorded with it, and History shows "by Canon Agent for Jane".
- **One open request per value.** If one is open, the agent adds evidence to it
  instead. It can replace its own with `supersedeOwnOpen`.
- **`dryRun`** goes through the same checks and returns the same diff without
  keeping anything, so the agent can show it first.
- **Retries are safe.** A repeated `idempotencyKey` returns the first result;
  the same key with different arguments is refused.
- At most 60 writes a minute per key.

### Setting up a Canon Agent

1. Create an [agent user](#agent-users) named **Canon Agent**, with no app roles.
2. On its page, create an API key with **Propose Canon changes**,
   **Edit aliases**, and **Act for linked users** if it serves several people.
3. In **Canon Settings**, give that user **Edit** on each data type it should
   fill in. Never **Review**: the Permissions panel warns if it has it.

## Item aliases

A key with **Edit aliases** can manage item aliases, for example to record each
item's WooCommerce product id so agents can look items up by it
(`search_items` matches aliases).

| Tool | What it does |
| --- | --- |
| `add_item_alias` | Adds an alias of an existing type. For a unique type, a name another item already has is refused, with that item. |
| `update_item_alias` | Renames an alias or moves it to another type (not to or from Supplier). |
| `remove_item_alias` | Removes an alias. The item's activity log keeps what it was. |

Alias types are managed in **Settings → Inventory → Alias Types**, where a type
can be marked **Unique** (one item per name, e.g. a WooCommerce ID). A type can
only become unique once no two items share a name of it. These tools take the
same `idempotencyKey` and `dryRun` as Canon proposals, and every change is
logged on the item.

## Receiving alerts

`get_receiving_issues` is meant for polling. A scheduled Hermes job can call it
with `since` set to its previous run and message the right people about new
failed inspections, missing COAs or lot mismatches, with a link to the
receiving page. Nothing in receiving waits on these alerts; they're a nudge.

## Hermes and chat apps

A shared agent like Hermes uses one API key for everyone who messages it. To
let people act from WhatsApp, Discord, Telegram, Slack or a Hermes session
under their own name (reviewing pricing, proposing Canon changes, editing
aliases):

1. A system admin creates a key for Hermes, ideally on its own
   [agent user](#agent-users), with **Act for linked users** ticked
   (or clicks **Act for linked users** on an existing key). Don't also give it
   write access unless Hermes should act as the key's owner.
2. Each person links each account once. In **Settings → User → Agents →
   Linked Accounts** they click **Link account**, pick the app, and send the
   code it shows to the bot from that account (a DM on Discord, Telegram or
   Slack; for Hermes, a desktop or CLI session of the profile). The code works
   once and expires after 10 minutes. Sending it proves they control both the
   Lumexia account and the chat account. A person can link as many accounts
   as they like; linking an account someone else had moves it to them.
3. From then on, Hermes passes the sender's account with each request and
   Lumexia acts as the linked user. An unlinked account is refused, with
   instructions for linking.

Hermes desktop and CLI sessions are identified by their profile, from the
`X-Lumexia-Agent-Identity` header in [the profile's config](#connect-hermes),
so linking one links that profile on that machine.

Everything done this way is also logged with the key, the key's owner, and the
account it came from (and the agent's session id when it sends one). People
can see and unlink their accounts in **Linked Accounts**; admins can unlink
anyone's from **Settings → Users → (user) → Agents**. Five wrong codes from one
account lock it out of linking for an hour. A key that acts for linked users
never reviews pricing as its owner.

<Callout type="warn">
  Lumexia trusts the account id Hermes sends for chat apps. Configure Hermes so
  the sender's id comes from the message metadata, not from anything the model
  could be talked into typing, and keep approvals to one-to-one chats.
</Callout>

## Security notes

- **Plain HTTP.** The key travels unencrypted, so anyone who can watch traffic
  on the network could read it. That's acceptable on a trusted network. For
  more, put Lumexia behind TLS (e.g. Caddy with its internal CA, or
  `tailscale serve`). Clients just switch the URL to `https://`.
- **Revoking is immediate.** A revoked or expired key is rejected on its next
  request. Disabling a user (or agent user) also disables all of their keys.
- **Keys are never stored.** Lumexia keeps only a SHA-256 hash and the first
  few characters (shown in the list) to tell keys apart.
- **Download links** are signed for one document and the key that asked for
  them, expire after 15 minutes, and stop working if the key is revoked.
- **Upload links** carry their own token instead of the key, so the key never
  ends up in a shell command. A link works once, expires after 15 minutes, and
  stops working if its key is revoked or loses write access. Agents can only
  attach files they uploaded with the same key.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| `401 Missing or invalid API key` | The header is missing, the key was mistyped, or it's revoked or expired. Check its status on the **Agents** tab. |
| `405 Method not allowed` | The endpoint is stateless and only accepts `POST`. Make sure the client is set to the **HTTP** (streamable HTTP) transport, not SSE. |
| `get_item_canon` returns no entries | No Canon data types apply to that item, or the database's static records don't match the build. See [Static Records](/docs/StaticRecords). |
| No upload, attach, or pricing review tools | The key is read-only. Ask a system admin to allow write on it (or **Act for linked users** for a shared agent). |
| "This WhatsApp account isn't linked" (or Discord, …) | The sender hasn't linked that account. They create a code under **Settings → User → Agents → Linked Accounts** and send it to Hermes. |
| "Hermes sessions are identified by their profile" | The profile's Lumexia server config is missing the `X-Lumexia-Agent-Identity` header. See [Connect Hermes](#connect-hermes). |
| `AGENT_MUST_NOT_REVIEW` | The agent's user can review that data type. Remove its Review grant in **Canon Settings**. |
| "idempotencyKey … was already used for a different request" | The agent reused a key for a different change. Each intended change needs its own key. |
| "Rate limit" | More than 60 writes in a minute from one key. Wait a minute and continue. |
| "Only pricing examinations that are pending review can be approved" | It was already approved or rejected, or is still queued. Check with `search_pricing_examinations`. |
| Upload link returns `403` | The link was already used, expired (15 minutes), or its key was revoked or made read-only. Get a new link. |

## For developers

- The route is `app/api/mcp/route.ts`. It authenticates the bearer key, then
  serves one request with a fresh `McpServer` using the SDK's
  `WebStandardStreamableHTTPServerTransport` (stateless, JSON responses).
- Keys live in the `api_keys` table. `lib/apiKeys.ts` creates,
  authenticates, lists, and revokes them.
- Tools live in `lib/mcp/tools/`. Each file exports a `ToolRegistrar` that
  receives the server and the caller's context (`ctx.user`, `ctx.scopes`), and
  is listed in `lib/mcp/server.ts`.
- Tools call Prisma and `lib/canon` directly with `ctx.user.id`. Don't reuse
  server actions that call `getUser()`. They depend on a browser session and
  redirect when there isn't one.
- Return `jsonResult(data)` for answers and `errorResult(message)` for misses
  the agent should react to. Keep payloads compact and capped.
- Keys carry `scopes`: `read`, plus `write`, `delegate`, `propose` and
  `alias:write` when an admin grants them (`grantableScopes` in
  `lib/apiKeys.ts`). Tools for each are registered only for keys with that
  scope in `lib/mcp/server.ts`, so other agents never see them.
- Write tools that create records go through `runWrite` in `lib/mcp/writes.ts`:
  a per-key rate limit, idempotency keys stored in `api_idempotency_keys`, and
  dry runs that run the real code in a transaction and roll it back.
- `ctx.origin` is the address the agent reached Lumexia at; use it for links
  handed back to the agent.
- Keys with the `delegate` scope act for linked users. Linked identities and
  link codes live in `linked_identities` and `identity_link_codes`
  (`lib/linkedIdentities.ts`; channels in `lib/identityChannels.ts`). Tools
  that act for someone take `actingFor` and resolve it with `resolveActor` in
  `lib/mcp/actingFor.ts`, which also reads the Hermes profile header.
- Canon proposals call `lib/canon/changeRequests.ts`, the same code as the
  Canon tab, with `skipSelfApproval` and the caller's transaction. Alias writes
  live in `lib/aliases.ts`, whose uniqueness check the item alias dialog uses
  too.
- Pricing approval and rejection live in `lib/pricing/examinationReview.ts`,
  shared with the pricing review page.
- Document downloads: `lib/apiDownloads.ts` signs links, and
  `app/api/mcp/downloads/[documentId]/route.ts` checks them and streams the
  file from storage.
- Document uploads: `create_document_upload` stores hashed, single-use tokens in
  `api_uploads` (`lib/apiUploads.ts`). `app/api/mcp/uploads/[token]/route.ts`
  takes the file and stores it with `lib/files/storeUpload.ts`, the same code
  the app's upload route uses. Document changes go through
  `lib/itemDocuments/mutations.ts`, which the Files tab uses too.
- Document inbox: `app/api/inbox/documents/route.ts` takes uploads from
  automations and calls `lib/documentInbox/ingest.ts`. Filing, taking back,
  checking and dismissing live in `lib/documentInbox/mutations.ts`, shared by
  the inbox page and `lib/mcp/tools/inbox.ts`. Arguments that name items,
  types, suppliers, lots and POs are resolved in `lib/mcp/documentArgs.ts`.
