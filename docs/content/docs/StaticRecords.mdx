---
title: Static Records
description: What static records are, how their IDs are deterministic, and how that makes a prebuilt image match every database
---

Static records map a human-readable name to a **database row ID**. They live as
generated TypeScript files under `configs/staticRecords/` — one file per model —
and let application code reference rows by name instead of hardcoding IDs:

```ts
import { recordStatuses } from "@/configs/staticRecords/recordStatuses";

// resolves to that row's ID
where: { statusId: { not: recordStatuses.archived } }
```

A generated file looks like this:

```ts
// configs/staticRecords/recordStatuses.ts
export const recordStatuses = {
  "archived": "cd5f3f81-493b-4bc0-9637-a36f7157e150",
  "active":   "d7b0a804-52c6-4586-b4f4-0fe49895f794",
  "inactive": "b674f2fc-6559-421d-9b72-88ee0cba2fa2",
} as const;
```

## The IDs are deterministic

Each ID is **derived from the record's table and name**, not randomly generated.
`scripts/generate/staticRecordId.ts` computes it as:

```ts
uuidv5(`${table}:${name}`, NAMESPACE)   // e.g. "requestStatuses:requested"
```

Because the same name always hashes to the same UUID, **every environment agrees**
— the ID for `recordStatuses.active` is identical in dev, CI, and production.

<Callout type="warn">
  Never change the `NAMESPACE` constant in `scripts/generate/staticRecordId.ts`.
  It would change every derived ID, and existing databases (whose rows were seeded
  with the old IDs) would no longer match.
</Callout>

## Why this matters

The generated files are statically imported throughout the app, so `next build`
**compiles their values directly into the `.next` bundle**. Deterministic IDs are
what make that safe: the values baked into the image are the *same* values the
seeder writes into the database, so a **prebuilt image matches any seeded
database by construction** — no per-environment regeneration, and no rebuild after
deploy. This is what lets the server pull and run an image it never built (see
[Deployment](/docs/Deployment)).

## How they are generated

The files are **gitignored** (only `configs/staticRecords/.gitkeep` is tracked)
and produced by generation. There are two equivalent generators:

| Script | Needs a DB? | Used by |
| --- | --- | --- |
| `scaffold-static-records` (`scripts/generate/scaffold.ts`) | No | The image build (`Dockerfile`) — derives IDs straight from the seed definitions in `scripts/initialization/data/*`. |
| `generate-static-records` (`scripts/generate/main.ts`) | Yes | Local dev and the seed pipelines — reads the IDs back out of the database. |

Both produce **identical** output, because the seeder inserts the same
deterministic IDs it would derive. The image is built with the DB-free scaffold
step, so no database is required at build time:

```dockerfile
RUN npm run scaffold-static-records
RUN npm run build
```

## Seeding

`npm run init` inserts each static record with its deterministic ID (see
`scripts/initialization/main.ts`). So after seeding, the rows in the database
carry exactly the IDs already compiled into the image — they match automatically.

Seeding happens on first boot for an empty database, or explicitly via
`npm run db:start` / `npm run db:demo:start`. See [Deployment](/docs/Deployment)
for the full flow.

## Quick reference

| Script | When | What it does |
| --- | --- | --- |
| `scaffold-static-records` | Image build | Derives real IDs from the seed data with no DB. |
| `generate-static-records` | Local dev; seed pipelines | Reads IDs from the DB and writes the maps (same values). |
| `init` | Seeding | Inserts reference data using the deterministic IDs. |
